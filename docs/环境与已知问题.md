## 2. 临时目录权限（Windows 沙箱特有，必读）

### 症状

`python -X utf8 -m unittest discover -s tests -v` 时 21 项测试全部 error，报：

```
PermissionError: [WinError 5] 拒绝访问。: '...\\tmpXXXXXXXX\\<子路径>'
```

### 原因

本机 DSH Windows 沙箱下，用 `tempfile.mkdtemp()`（内部按 `mode=0o700` 创建）建出来的目录会带上当前进程无法访问的 ACL；之后在该目录里再建子目录就被拒绝。实测以默认/`0o777` 权限创建的目录完全正常，所以问题不在代码逻辑，而在临时目录的权限继承。

### 已内置的修复

`tests/__init__.py` 与 `tools/__init__.py` 各有一段 Windows 兼容层，把 `tempfile.mkdtemp` 替换为用 `os.makedirs`（默认权限）创建 `tmp + uuid4().hex`。因为 `unittest discover -s tests` 与所有 `tools/*` 都会先导入包 `__init__`，修复对所有测试/工具生效。改后实测 `Ran 21 tests ... OK`。

**不要删除或绕过这两处兼容层**，否则自测会整批 error；也不要把它当成业务代码改回去。

### 新机器上遇到同样报错时

1. 先确认是否在受限沙箱/受管终端里跑；换普通 PowerShell 或 CMD 再试。
2. 把 `TMP`、`TEMP` 指向自己有完全控制权的目录（例如 `D:\tmp`）后重试。
3. 只有单元测试的 fixture 用到临时目录；训练、打包、核验都不依赖它，所以此问题不会污染实验产物。

## 3. run 目录并发（血的教训）

同一个 `runs/baselines/<exp>_seed<seed>/` **只能有一个进程写**。2026-11-22 曾因中断后自动续跑 + 手工重启同时触发，两个 trainer 同时向 `G_seed29/metrics.jsonl` 追加，出现 epoch 14–19 重复行（同 epoch 的 dev 值一样、`seconds` 不同）。

- 事故记录：`validation/G_seed29_duplicate_incident.json`
- 隔离证据：`validation/quarantine/G_seed29_20261122_123643/`（仅日志，checkpoint 已删）
- 现在的 `runs/baselines/G_seed29` 是从零重跑后的干净结果（20 epoch，best epoch 18，0.805）

接手时：启动前先确认没有残留训练进程；不要用两个终端同时 `run_baselines`；中断后只用一个入口续跑（`tools/run_baselines.py` 会自动对已有 `last.pt` 追加 `--resume`）。

## 4. 计时异常

`G_seed17` 的 `metrics.jsonl` 中某一 epoch 的 `seconds` 约 30,600 秒（8.5 小时）。原因是暂停期间进程被挂起、计时继续累计，**不是真实训练速度**。做成本分析请用中位 145 秒/epoch，不要用日志合计。

## 5. 工具的阶段限制

| 工具 | 现在能否跑 | 说明 |
|---|---|---|
| `unittest discover -s tests` | 能，21 项 OK | 需要第 2 节的兼容层 |
| `tools.verify_data_handoff` | 能 | 校验 8,000 张训练图哈希、划分、统计、真实 batch |
| `tools.progress_report` | 能 | 允许未跑满的 run，输出 `results/handoff/` |
| `tools.package_team --verify .` | 能 | 校验包内 MANIFEST |
| `tools.summarize_baselines` | **不能** | 要求 6 个 run 均 1..20 epoch，缺一即报错 |
| `tools.audit_delivery` | **不能** | 要求 `results/baselines/*` 与 6 个完整 run，属最终交付核验 |
| `tools.check_archive --with-baselines` | **不能** | 需重放 6 套 best.pt，等六次跑完再用 |

上面三个"不能"是设计上的最终门槛，不是环境故障；六次跑满后自然通过。
